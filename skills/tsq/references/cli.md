# The `tsq` CLI

Installing and pinning the generator, every command and flag, what `tsq gen` writes, the migration
sections of the generated `.sql` files, and `tsq.json`. Directive syntax is in `annotations.md`;
what the generated Go code declares is in `generated-code.md`.

## Install and pin

```bash
go get github.com/tmoeish/tsq/v5@latest                     # the library, in go.mod
go install github.com/tmoeish/tsq/v5/cmd/tsq@latest         # the CLI, on PATH
```

The CLI and the library are one module with one version. **Run the CLI at the version `go.mod`
requires**: the generated file header records the generator's version
(`// Code generated by tsq-vX.Y.Z. DO NOT EDIT.`), `tsq.json` records it too, and a CLI older or
newer than the library produces churn in every regenerated file (an older CLI refuses a `tsq.json`
a newer one wrote, naming the version to install). Two ways to keep them in step:

```bash
go install github.com/tmoeish/tsq/v5/cmd/tsq@v5.0.0         # pin the binary to the go.mod version

go get -tool github.com/tmoeish/tsq/v5/cmd/tsq              # or track it in go.mod as a tool
go tool tsq gen ./internal/database                         # ...and run it through go tool
```

`go get -tool` records the CLI under the same module requirement as the library, so upgrading one
upgrades the other. Upgrading TSQ means: bump the version, regenerate every package, commit the
result (see "Upgrading TSQ" below).

TSQ ships no database driver: the project adds the one it uses (`modernc.org/sqlite`,
`github.com/mattn/go-sqlite3`, `github.com/go-sql-driver/mysql`, `github.com/jackc/pgx/v5/stdlib`
or `github.com/lib/pq`; see `runtime.md`).

## Commands

```txt
tsq gen <package-or-dir> [--check | --dry-run] [-v]
tsq version [--short | --json]
tsq --version                 # one line: tsq version vX.Y.Z
tsq help [command]            # also tsq <command> --help / -h
```

### `tsq gen`

Generates code for **one Go package** per run. The argument is a module import path
(`github.com/acme/app/internal/database`), a relative directory (`./internal/database`, resolved
from the current directory, so run it from the module root) or an absolute directory. Flags may come
before or after the argument.

| flag | effect |
| --- | --- |
| *(none)* | write every generated file that changed, remove generated files the sources no longer produce |
| `--check` | render in memory, write nothing, exit 2 when any generated file is out of date |
| `--dry-run` | render in memory, write nothing, print each file as `CREATE`, `UPDATE`, `UNCHANGED` or `STALE` (to be removed), then a `files: N create, N update, N unchanged, N stale` summary |
| `-v`, `--verbose` | print each generated file path |
| `-h`, `--help` | print the command's help |

Exit status: `0` on success, `2` when `--check` finds generated files out of date, `1` for any other
error (the package does not load, a directive is invalid, a file is not TSQ's to overwrite). CI can
therefore tell "run `tsq gen`" from "the package is broken". Validation errors start with the
offending struct's or field's `file:line:column`.

There is no formatting step: `//tsq:` directives are comment lines gofmt leaves alone.

Overwrite rules: `tsq gen` creates missing files, atomically replaces a file that starts with
`// Code generated by tsq-`, does not rewrite a file whose content would not change, and **refuses to
overwrite any other file** (a hand-written `user.tsq.go` stops the run). A generated file whose
struct no longer exists is removed.

Warnings go to stderr and do not fail the run: an index or row that MySQL's limits refuse, a
backslash in a string default (it means different things per engine), and every destructive
statement a migration section leaves commented out. They repeat on every run until the cause is
gone.

### `tsq version`

```bash
tsq version           # version plus build time, commit, branch, Go version, platform
tsq version --short   # just the version string, for scripts
tsq version --json    # the same fields as JSON: version, build_time, git_commit, git_branch, go_version, platform, arch
```

Build time, commit and branch are injected at link time. A CLI obtained with `go install` reports
`unknown` for those three; that is expected. Binaries from GitHub Releases carry the real values.

## What `tsq gen` writes

Into the package directory, beside the annotated structs:

| file | content |
| --- | --- |
| `<struct>.tsq.go` | one per `//tsq:table` struct: the `XxxTable` type, the `TableXxx` value, row methods (`generated-code.md`) |
| `<struct>.result.tsq.go` | one per `//tsq:result` struct: the `XxxResult` type and `ResultXxx` value |
| `runtime.tsq.go` | `TSQTables()`, every table of the package, for `tsq.Open` / `tsq.NewRuntime` |
| `sqlite.sql`, `mysql.sql`, `postgres.sql` | the schema per dialect, then one dated migration section per later change |
| `tsq.json` | the schema history the `.sql` files are rendered from, and how each dialect spelled each column |

File names are the lowercased struct name (`OrderItem` → `orderitem.tsq.go`). Commit all of them,
`tsq.json` included: without it the next run cannot write a migration, and `tsq gen` refuses to run
when the `.sql` files exist without it rather than start the history over. Never hand-edit any of
them; change the struct or directive and regenerate.

In CI, run `tsq gen --check <package>` for each generated package (exit 2 means someone forgot to
regenerate). Judge freshness with `--check`, not `git diff`.

## Migration sections in the `.sql` files

Each `.sql` file holds the full schema followed by one dated migration section per `tsq gen` that
changed it. A section in `postgres.sql` is one transaction (`BEGIN;` … `COMMIT;`): run it in one
session (psql, or any tool that runs the file on one connection) and a statement the database refuses
undoes the whole section, even under psql without `ON_ERROR_STOP`. Sections in `mysql.sql` and
`sqlite.sql` are not: MySQL commits every DDL statement on its own, and SQLite's table rebuild takes a
transaction of its own; there a refused statement leaves the ones before it applied, so run a section
that retypes a column over rows on a copy of the data first. A migration tool that wraps every file
in a transaction of its own (Flyway, goose) only warns about the nested `BEGIN`. A migration never runs a destructive statement for you:

- a `DROP TABLE`, a `DROP COLUMN`, or a SQLite rebuild that leaves a column out is written commented
  out behind `-- DESTRUCTIVE`, and `tsq gen` warns about it. Renaming a table or a `db` tag, and a
  mistyped directive, look the same to the generator as removing it, so run it by hand only once the
  drop is meant. A comment that reads like a directive but is not one (`// tsq:table`, with a space)
  is reported too
- indexes are dropped before the columns they name, and before any table's changes, since index
  names are global on PostgreSQL and SQLite: an index moving to another table, or a renamed table
  keeping its index names, does not collide with the old one. A unique index recreated under a name
  the section drops first (an index that became unique, or changed columns) fails after the DROP
  where rows share its values, leaving the table with neither on MySQL and SQLite (on PostgreSQL the
  section rolls back): the file says so before the DROP,
  with the columns to check (the runtime's `Reconcile` builds such an index under another name
  first, and refuses before any DDL where rows share the values)
- a column that becomes NOT NULL is filled for the rows holding NULL first, with its default or its
  type's zero value, on every dialect (`UPDATE ... WHERE col IS NULL` on MySQL and PostgreSQL, the copy
  of a SQLite rebuild), and the section says with what. A new NOT NULL column without a default gives
  the rows present the zero value the same way: added with that default, which is then dropped
- a changed `generated:` expression is left to a migration you write, with a comment saying so
- a `db` tag renamed only in case is a column rename: `RENAME COLUMN` on PostgreSQL, and a comment on
  MySQL and SQLite, which match column names without case. Any other renamed field or `db` tag is,
  to the generator, one column dropped and one added: the section adds the new column empty and
  leaves the `DROP` commented. Where the two have the same shape, the section starts with the
  `ALTER TABLE ... RENAME COLUMN ... TO ...` that keeps the data, commented, to run instead. A table
  whose `name=` changed is likewise one table dropped (commented) and one created: where the columns
  are the same, the section starts with the commented `ALTER TABLE ... RENAME TO ...` and the renames
  of its indexes (their names derive from the table's), to run instead of both tables' sections
- a type change SQLite does not enforce (a `VARCHAR` size, `INT` to `BIGINT`) does not rebuild the
  SQLite table. PostgreSQL writes `USING` only between kinds that have no assignment cast (`BOOLEAN` to
  `INTEGER`): a shorter `VARCHAR` is changed without it, so a value that does not fit fails the
  migration instead of being cut. Where it does write one, a character type converts through `TEXT`
  for the same reason: `type:TEXT` to `size:5`, or an integer to a short string, fails on a value that
  does not fit. Widening an auto-increment key widens its sequence too. A primary key that generates
  nothing (a table another tool created with a plain key) where the declaration generates its keys
  gets a generator under `Reconcile` on every engine: MySQL's `AUTO_INCREMENT`, a SQLite rebuild, and
  on PostgreSQL an identity column (`GENERATED BY DEFAULT AS IDENTITY`) started past the rows
  present. The other way round, a key the caller assigns (`pk=ID assigned`) over a column that
  generates one, drops the generator (MySQL's `AUTO_INCREMENT`, PostgreSQL's identity or `SERIAL`
  default). On SQLite an integer key is the rowid, which the database assigns whether or not
  `AUTOINCREMENT` is written and takes when given: such a column matches a key declared either
  way, and nothing is changed
- a type change carries the values over or fails; it never leaves them changed without a word, and the
  three dialects end up holding the same thing. Bytes and text keep their bytes (`convert_from` /
  `convert_to` on PostgreSQL, whose casts would write `abc` as `\x616263` and read `\101` as `A`), a
  fraction becomes the nearest integer, and a number that becomes a boolean is true unless it is zero
  (`USING c <> 0` on PostgreSQL, an `UPDATE` before the `MODIFY` on MySQL, the copy of a SQLite
  rebuild). Text that becomes a number, a boolean or a time fails on MySQL and PostgreSQL at the value
  that does not convert. SQLite keeps any value under any type, and a script cannot refuse one, so
  there that change is written as a comment (`manual rebuild required: ...`) and left to you;
  `SchemaPolicyReconcile` does make it when every value converts
- `tsq gen` prints the warnings about drops written commented out on every run, and does not write
  again a generated file whose content would not change
- `tsq.json` holds the history the `.sql` files are rendered from: keep it in version control. `tsq gen`
  refuses to run when the `.sql` files exist without it, rather than start the history over and lose
  the changes since the last run
- `tsq.json` also records how each dialect spelled each column the last time the files were written
  (its `renderings`). A new version of TSQ that spells a column otherwise with no change in your
  model — a default written in UTC, a range constraint, a type with its precision — is a change of
  the schema the runtime declares, and the files get a dated section for it like a model change
  (`respell column qty (postgres: range check; sqlite: range check)` in the history): `ALTER` statements on MySQL and
  PostgreSQL, a rebuild on SQLite where the default or the constraint is concerned, nothing to run
  where only a type's spelling within one SQLite affinity moved. After upgrading TSQ, `tsq gen --check`
  fails until `tsq gen` has written that section, as it does for a model change. Files written before
  renderings were recorded have none to compare: the first run records them, and a respelling from
  before that is not written as a section (the runtime's `Validate` names it and `Reconcile` makes it).
  The other way round, a `tsq.json` written by a newer TSQ is refused by an older one, with the version
  to install: rewritten by the older CLI, the file would lose what the newer one records, and the two
  would hand it back and forth, each writing a migration for the other's spelling. Keep one `tsq` version
  per repository (pin it in CI)
- SQLite changes a column type, or adds a generated column, a column whose default is not a constant
  (`CURRENT_TIMESTAMP`, which adding `created_at` has) or a NOT NULL column without a default, by
  rebuilding the table, since `ADD COLUMN` refuses those on a table with rows: it creates the
  new table, copies the rows, drops the old one and renames the new one, with foreign keys off. The
  copy cannot fail on a table with rows: a new NOT NULL column without a default gets its type's zero
  value (the section says so), and a generated column is computed by the new table. Triggers on the
  table are dropped by the rebuild and must be created again; the section says that too

## Upgrading TSQ

1. bump the library: `go get github.com/tmoeish/tsq/v5@vX.Y.Z` (and the pinned CLI)
2. run `tsq gen` on every generated package: the file headers carry the version, and a new version
   may spell a column differently, which becomes a dated "respell" migration section
3. run the project's tests and commit the regenerated files together with `go.mod`

## Stale generated files

Generated code builds no query at package initialization, so a generated file that no longer
matches its struct fails to compile, or reports a definition error from every query and write
that uses the table (`TableXxx.Err()`), instead of panicking on import. The usual causes:

- directives or fields changed and `tsq gen` was not rerun
- the TSQ version changed and the generated files were not regenerated
